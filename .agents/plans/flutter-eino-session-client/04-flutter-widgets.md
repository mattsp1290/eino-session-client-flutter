# W4 — Themeable Flutter widgets

Goal: small reusable text/tool/input widgets usable with either adapter. Prerequisites W1/W2; widget implementation can proceed alongside W3 after shared state contracts stabilize. Changes: new W1 widget files plus `test/transcript_view_test.dart`, `test/tool_activity_list_test.dart`, `test/agent_input_test.dart`, `test/accessibility_test.dart` under the new widget test parent. No application workflow migration or feature flags.

`TranscriptView` consumes immutable `MessageView` values and shows permitted user/assistant text in stable-ID keyed rows. Use lazy list construction. Do not retain an additional event history. Render plain escaped/selectable text; Markdown, links that automatically launch, arbitrary HTML and model-driven actions are excluded. Show explicit stale/incomplete/omitted-history and live-unavailable labels when present. Scroll only when the user is near the trailing edge; do not steal focus or jump a user reading older messages.

`ToolActivityList` shows names and safe statuses keyed by tool ID. Repeated names remain distinct rows. Arguments complete and result observed are different from authoritative Eino completed/failed/interrupted. Use text/icons in addition to color. There are no approval buttons in the initial widget set. Render generic paused execution as a fixed “Waiting for host action” status, distinct from completed and Eino interrupted, without retaining/rendering interrupt payloads or adding resume controls.

`AgentInput` accepts a host `Future<void> Function(String)` submit callback, enabled/busy state and optional host interrupt callback. Blank text does not submit. Prevent duplicate sends while the callback is pending. Retain typed input on failed submission and clear only after accepted submission according to the callback contract. Distinguish local disconnect from server interrupt in labels. A successful interrupt callback does not settle a tool/run. Host callbacks decide all application actions and authority.

Use ambient `ThemeData`/`ColorScheme`, inherited text scale and optional labels/style overrides. No fixed application colors, logos, routes, provider lookups or state-management library. Widgets receive state via arguments; an example host may attach a core listener and call `setState`. Widgets never own the injected controller/transport. If input accepts an external text controller or focus node, ownership is explicit: dispose only internally created instances, detach listeners from borrowed instances.

On unmount, remove listeners and cancel widget-local scheduling; any pending host future must check mounted before touching widget state. Do not cancel a host-owned run or dispose a host controller implicitly. The example host owns adapter/controller cleanup in its lifecycle.

Acceptance tests run light/dark themes at 320 logical pixels and 200% text scaling without overflow, plus long words/tool names and empty/error/stale transcripts. Test Tab focus order, visible focus, keyboard submission behavior, disabled/busy actions and semantic labels/status without color dependence. Announce run/connection status changes without speaking every token. Verify scroll anchoring, stable keys for repeated tools, borrowed resource preservation, unmount during active submission and removal of controller listeners. Decode an SDK interrupt-outcome response into the host/controller and assert visible/semantic paused status, no success announcement or action button, and preserved status after response cleanup. `flutter analyze` and `flutter test` must pass. W5 web builds and real example smoke tests prove widgets are usable in a plain Flutter host.
